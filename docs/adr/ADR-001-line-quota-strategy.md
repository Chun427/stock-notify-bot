# ADR-001：LINE 推播額度策略

## 狀態

提案（Proposed）。**本 ADR 不含實作**，僅供決策參考。

## 背景

台灣 LINE 官方帳號「輕用量方案」：月費 0 元，內含 **200 則/月**免費訊息。

現行架構每個交易日對每個市場各推 3 次（開盤／盤中／收盤），兩個市場合計每日 6 則，
LINE、Telegram 雙管道同時發送（見 README「雙管道推播」）：

```
6 則/日 × ~22 個平日/月 ≈ 132 則/月
132 / 200 ≈ 66% 額度使用率，餘裕約 1.5 倍
```

2026-07-30 已實際發生 LINE HTTP 429（"You have reached your monthly limit"）。
經診斷（見對話紀錄 P1），確認**並非重複觸發造成**——07/16–07/29 連續兩週，
每個 slot 每天恰好觸發 1 次，無異常。真正的問題是：**132/200 的餘裕本身就不夠穩健**。
只要多一個推播時段、多一個收件對象、或月底多幾次手動補播，就會撞牆。

429 發生當月的確切成因（是否真的達到 132、或是計數方式與預期不同）需查
LINE OA Manager 後台的實際計數，本 ADR 不依賴那個數字成立——即使本月剛好沒撞牆，
1.5 倍餘裕仍是架構層級的風險，遲早會在假期少、補播多、或標的增加時觸發。

## 方案

### 方案 A：LINE 僅推收盤（台股 13:35 + 美股 16:05 ET）

- **月用量估算**：2 則/日 × 22 ≈ **44 則/月**，額度使用率 22%，餘裕 4.5 倍
- **失去什麼**：開盤、盤中兩個時段沒有 LINE 通知，只剩 Telegram
- **README 契約影響範圍**：
  - 「雙管道推播」章節需註明 LINE 為「僅收盤」而非「與 Telegram 同步全時段」
  - 「自動推播排程」表格需標示各 slot 的實際推播管道（不再是兩管道對稱）
  - `notify/line.py`（或遠端 `line_notifier.py`）呼叫時機需新增 slot 判斷邏輯
  - Fail-safe 表不受影響（沒發送不算失敗）
- **理由傾向**：美股盤中／收盤本來就設定「靜音」（`disable_notification`），
  這兩則對使用者的即時提醒價值本來就最低，砍掉的是使用者最不會即時看的通知

### 方案 B：LINE 僅推台股（3 個 slot，不含美股）

- **月用量估算**：3 則/日 × 22 ≈ **66 則/月**，額度使用率 33%，餘裕 3 倍
- **失去什麼**：美股全部 3 個時段都沒有 LINE 通知，只剩 Telegram
- **README 契約影響範圍**：
  - 同方案 A，但影響範圍更大——「雙管道推播」變成「LINE 僅台股、Telegram 兩市場都推」，
    需要更明確的文字說明避免使用者誤解
  - 需要在 `notify` 層新增 market 判斷邏輯
- **取捨**：比方案 A 保留更多餘裕，但犧牲的是「美股」這整個市場的 LINE 覆蓋，
  對本來就習慣看美股盤後消息的使用者影響較大

### 方案 C：升級中用量方案（NT$800/月，3,000 則）

- **月用量估算**：無需改動推播邏輯，132/3,000 ≈ 4.4% 額度使用率，餘裕極大
- **失去什麼**：不失去任何功能，純粹付費換餘裕
- **README 契約影響範圍**：無——不涉及任何格式、排程、管道邏輯變更
- **代價**：NT$800/月 × 12 ≈ **NT$9,600/年**，對一個自用 bot 而言是否划算需你自己評估
- **額外考量**：即使升級，若日後標的數量增加或推播頻率提高，仍可能再次逼近新的額度上限，
  只是把同樣的風險往後推延，而非消除

## 建議方案

**傾向方案 A**（LINE 僅推收盤）。理由：

1. 犧牲的兩個時段（開盤、盤中）本來就不是使用者最需要即時反應的時刻，收盤才是「今天結果」的總結
2. 餘裕 4.5 倍，遠比現行 1.5 倍穩健，且不花任何費用
3. 相較方案 B，仍保留美股在使用者最關心的「收盤結果」上的 LINE 覆蓋，只是犧牲時段而非整個市場
4. 方案 C 是延後問題而非解決問題，且需要持續付費

但這是使用習慣層面的取捨（你多常看 LINE 的開盤/盤中通知），最終判斷應由你決定。

## 重要：此變更觸及 README 凍結章節，需先確認 README 同步修訂

本 ADR 討論的任一方案（A 或 B）都會改變「雙管道推播」與「自動推播排程」兩個章節
目前描述的行為（目前 README 隱含「兩管道、六個 slot 完全對稱推播」）。
依專案契約規則，**不得為了配合實作而修改 README，也不得在 README 未同步更新前
逕行變更 production code**。若採納 A 或 B，必須：

1. 先修訂 README 對應章節，明確寫出「LINE 僅推 X」的新契約
2. 待 README 定稿後，才進入實作與測試（含新增「LINE 僅特定 slot/market 才發送」的契約測試）
